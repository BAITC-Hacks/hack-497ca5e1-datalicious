## Как работает агент

Модель получает исходный `SimulationResult` и цель повысить Score. Она выбирает
инструменты и аргументы, сервер возвращает результаты по `call_id`, после чего
модель выбирает следующий шаг. Готового списка кандидатов или перебора на сервере нет.

1. `get_city_context({})` возвращает копию существующего датасета: показатели,
   каталог, правила, лаги, конфликты, синергии. Формула здесь не реализуется.
2. `evaluate_scenario({ scenario })` передаёт кандидата в `engine.evaluate`.
   Допустимый вариант сохраняется под ID `candidate-N`; исходный имеет ID `original`.
   Невалидный возвращает доменные `issues` без Score. Его можно исправить следующим вызовом.
3. `compare_scenarios({ leftId, rightId })` сравнивает только сохранённые допустимые
   результаты. Разницы Score и стоимости считает сервер, не модель.
4. Финал модели — строгий объект `{ selectedScenarioId }`. Сервер проверяет ID и
   что это лучший сохранённый вариант, включая исходный. При равенстве сохраняется
   ранее зарегистрированный вариант. Неизвестный или не лучший ID — ошибка, не успех.

Zod у инструментов проверяет только транспортную форму, а не повторяет бизнес-правила.
В **аргументах инструмента** поле `districtId` обязательно и допускает `null`:
перед доменом `null` преобразуется в отсутствие поля. В **публичном HTTP-запросе**
для городской меры поле по-прежнему отсутствует. Общий `Scenario` не изменён.
Неизвестные инструменты, невалидные аргументы и непроверенные ID не исполняются,
а возвращают безопасную причину отказа модели.

Реестр живёт только внутри запуска. Повторный набор мер, даже с другим порядком,
берётся из кэша; это относится и к невалидным наборам. Одинаковые меры внутри
одного набора не удаляются: обнаружение дублей — задача домена. До успешного
завершения нужно хотя бы одно обращение к домену с отличающимся кандидатом.

Из ответа модели не отображаются произвольные числа или утверждения. Модель выбирает
проверенный ID, а сервер формирует текст из результатов движка: пять мер и районы,
Score, разницу с исходным, бюджет, слабейший район, критические показатели и
ухудшения отдельных показателей. `strengths`, `risks`, `consequences` явно относятся
к исходному сценарию; проверенная альтернатива и её компромиссы — в `recommendations`.
Это шаблонное представление фактов после **реального инструментального цикла**, а не
один запрос на объяснение. Если улучшения нет, вывод честно оставляет исходный вариант.
Глобальный оптимум не обещается. Решения пользователя автоматически не меняются.

### Лимиты, диагностика и токены

`AGENT_LIMITS`: максимум 6 запросов модели, 12 вызовов инструментов,
`max_output_tokens: 2000` на ответ, общий тайм-аут 45 секунд.
Каждая попытка учитывается до обращения к SDK. Для агентных запросов передаётся
`maxRetries: 0`; фабрика и поведение старого аналитика не изменены. Скрытых повторов
нет, включая HTTP 429 (проверено через настоящий SDK с подменённым `fetch`).
Timeout отдельного запроса — минимум между 20 секундами фабрики и остатком общего
лимита. По истечении 45 секунд запрос прерывается через `AbortController`.
Синхронный `engine.evaluate` нельзя прервать таймером внутри JS; после возврата
дедлайн проверяется снова. Домен должен оставаться быстрым чистым вычислением.
Если окружение развёртывания ограничивает запросы сильнее, команда должна согласовать
меньший агентный тайм-аут до подключения; конфигурация деплоя здесь не менялась.

Отказ, неполный ответ, некорректный финал, ошибка провайдера и исчерпание лимитов
дают `AI_UNAVAILABLE` (502). Частично найденное улучшение не выдаётся как успешный
поиск. Ошибка конфигурации — 503; исключение настоящего движка через адаптер — 500.

`runScenarioAgent` возвращает внутренние `bestScenarioId`, `bestResult`, `improved`,
`journal`, `usage` и совместимый `analysis`. При незавершённом поиске
`AgentSearchError` хранит причину, снимки журнала и usage. Журнал содержит инструменты,
ID вызовов/сценариев, проверенные решения, ошибки валидации и Score допустимых вариантов.
Он не содержит ключа, сырых исключений провайдера или скрытых рассуждений.
В историю запросов возвращаются необходимые модели reasoning items, но не в журнал/UI.

`usage` включает число запросов/инструментов и суммы `input_tokens`, `output_tokens`,
`total_tokens`, `cached_tokens`, `reasoning_tokens` из всех полученных ответов,
включая неполные. Сохраняется usage каждого ответа отдельно. Если данных нет —
`null` для этого ответа; суммарные значения отражают только известные данные,
а не доказательство нулевой стоимости. После сетевой ошибки или отмены стоимость
неизвестна. Цена в деньгах не рассчитывается: модель задаётся окружением, тариф не зашит.
Диагностика не добавляется в `AnalyzeResponse`, не логируется автоматически и
не сериализуется тайно в строках анализа.

```ts
import { simulationEngine } from "@/domain";

import { createAgentAnalysisService } from "@/server/agent";

export const runtime = "nodejs";
export const POST = createAnalyzeHandler({
  engine: simulationEngine,

});
```

Один и тот же настоящий движок проверяет исходный сценарий в обработчике и кандидатов
в агенте. Старый `analysisService` сохраняется,
но его подключение вместо нового адаптера даст аналитика, а не агента.

Обработчик проверяет только строгую HTTP-оболочку `{ scenario }`. Содержимое
`scenario` как `unknown` передаётся `engine.evaluate`. Домен должен проверять
структуру, лишние поля, ID, правила и возвращать нормализованный результат.
Ошибки с `INVALID_SHAPE` отображаются в HTTP 400; остальные доменные ошибки — в 422.
При смешанном списке наличие `INVALID_SHAPE` даёт 400. Сами `issues` сохраняются.
Невалидный сценарий не получает Score и не вызывает SDK.

При успешном расчёте сервис получает копию `SimulationResult`: изменение объекта
внутри стороннего адаптера не должно менять числа, возвращаемые сервером.
`contributions` — эффекты показателей до clip, а не аддитивные вклады в Score.
В сервисе, генераторе и тестовых двойниках нет второй реализации формулы.

После подключения требуется тест с настоящим доменом и mock OpenAI на
`exampleDecisions`: стоимость 95, база 52.55768, итог 56.54307 с допуском.
Сейчас эти значения используются только как явно обозначенная тестовая фикстура
в `src/server/__tests__/fixtures.ts`. Это не доказательство правильности движка.
В агентных тестах Score 60/61 — искусственные значения двойника для проверки протокола,
а не утверждения о реальном эффекте предложенных мер. Если настоящий код противоречит
организаторскому датасету/формуле, зафиксировать расхождение участнику №1; не менять
требования или ожидаемые доменные результаты под ошибочное поведение.

## HTTP-контракт для участника №2

`POST /api/analyze`, `Content-Type: application/json`.
Тело соответствует `AnalyzeRequest` из `@/domain/types`. Пример организаторов:

```json
{
  "scenario": {
    "decisions": [
      { "measureId": "M7", "districtId": "nura" },
      { "measureId": "M8", "districtId": "nura" },
      { "measureId": "M10", "districtId": "nura" },
      { "measureId": "M12" },
      { "measureId": "M5", "districtId": "saryarka" }
    ]
  }
}
```

Для M12 и других городских мер `districtId` отсутствует, а не равен `null` или
`"город"`. Не передавать Score, стоимость, эффекты, AI-инструкции или API-ключ.
Лишние поля верхнего уровня отклоняются; поля сценария проверяет домен.

| Статус | Ответ / обработка UI |
| --- | --- |
| 200 | `{ ok: true, result, analysis }` — `result` всегда исходного сценария; текст проверенной альтернативы — в `analysis.recommendations` |
| 400 | `INVALID_REQUEST` — неверный JSON, оболочка или структура сценария |
| 422 | `INVALID_SCENARIO` — показать `error.issues`, индексы решений с нуля |
| 501 | `NOT_IMPLEMENTED` — текущий маршрут ещё не подключён |
| 503 | `AI_NOT_CONFIGURED` — на сервере отсутствует ключ или модель |
| 502 | `AI_UNAVAILABLE` — отказ, неполный/невалидный ответ, тайм-аут или ошибка провайдера |
| 500 | `INTERNAL_ERROR` — непредвиденная внутренняя ошибка |

Все ошибки имеют форму `{ ok: false, error: { code, message, issues? } }`.
В ответах ошибок **нет** `result` и `analysis`. `issues` относится к доменной
валидации. Ошибка AI не должна стирать уже имеющийся локальный расчёт.

Пример сетевой функции для будущего UI (это инструкция, компонент здесь не создан):

```ts
import type { AnalyzeRequest, AnalyzeResponse, Scenario } from "@/domain/types";

async function requestAnalysis(
  scenario: Scenario,
  signal: AbortSignal,
): Promise<AnalyzeResponse> {
  const body: AnalyzeRequest = { scenario };
  const response = await fetch("/api/analyze", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body),
    signal,
  });
  // Ответ своего API имеет согласованный контракт; ошибки сети/JSON попадут в catch.
  const payload: AnalyzeResponse = await response.json();
  if (payload.ok && !response.ok) throw new Error("Несогласованный ответ сервера");
  return payload;
}
```

При обработке результата сначала проверить `payload.ok`:

- `true`: показать `analysis.summary` и списки `strengths`, `risks`,
  `consequences`, `recommendations`; пустые списки допустимы. Строки отображать
  обычным текстом через React, без `dangerouslySetInnerHTML`.
- `false`: показать `error.message`, для 400/422 — доступные `issues`.
  При 501 пояснить, что интеграция ещё не готова; при 502/503/500 дать возможность
  повтора, сохранив локальный результат текущего сценария.
- Отклонённый `fetch` или ошибка JSON: сетевое/неожиданное состояние, а не
  успешный AI-ответ. Отмену запроса не показывать как ошибку пользователя.

Участник №2 реализует skeleton, блокировку повторной отправки и версию сценария:
при запуске запомнить версию; при любом редактировании/сбросе увеличить её,
отменить прежний `AbortController` и убрать объяснение старого набора. Применять
ответ, ошибку и завершение loading только если версия всё ещё совпадает.
Отмена браузерного запроса сама по себе не гарантирует отмену запроса провайдеру.
В сравнении сценариев хранить объяснение рядом с соответствующим сценарием.

Числа показывать из `result.baseline`, `result.after`, `result.scoreDelta`,
`result.budget` и других расчётных полей, не извлекать их из текста LLM.
Показывать заголовок «AI-агент: поиск альтернативы», пояснять, что карточки и графики
относятся к исходному набору, а рекомендации — отдельное предложение.
Не заменять исходные решения, Score и графики на рекомендуемые без действия пользователя.
Текущий контракт позволяет только текстовую рекомендацию: пользователь вручную
выбирает перечисленные меры и заново считает. Не парсить строки рекомендаций ради
кнопки «Применить», не добавлять несуществующий `bestScenario` в клиентские типы.
Текущий `ProjectShell` этих действий ещё не реализует.

## Конфигурация AI

После подключения настоящего движка задать серверные `OPENAI_API_KEY` и
`OPENAI_MODEL` по существующему `.env.example`. Реальные значения хранить
в локальном окружении или `.env.local`, не в Git и не в `NEXT_PUBLIC_*`.
Модель должна поддерживать Responses API, function calling и структурированный ответ.
Конкретная модель не захардкожена, её доступность здесь не проверялась.

Существующая фабрика проверяет непустые значения, создаёт SDK только при анализе,
задаёт timeout 20 секунд на попытку и максимум один повтор SDK для старого аналитика.
Агент отключает повторы на уровне своих запросов и использует общий лимит выше.
Сырые исключения провайдера не возвращаются.

Агент использует `responses.create`, `zodResponsesFunction`, `zodTextFormat` и
`toResponseInputItems` установленного SDK по
[официальному руководству function calling](https://developers.openai.com/api/docs/guides/function-calling).
Старый аналитик использует `responses.parse` по
[руководству Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Zod подтверждает структуру, а не истинность свободного текста: поэтому агентный
отчёт строится сервером из реестра. Тесты с mock не оценивают качество живой модели.

## Структурированные альтернативы: предложение команде

Сейчас общий контракт не изменяется. Для интерактивного применения/сравнения
альтернатив предлагается **отдельное согласование**: в успешную ветку
`AnalyzeResponse` добавить необязательное поле
`agent?: { bestScenarioId: string; bestResult: SimulationResult; improved: boolean }`.
`bestResult.scenario` уже содержит решения и не требует дублирующего `bestScenario`.
`result` остаётся исходным. Поле появляется только после завершённого поиска;
при отсутствии улучшения `bestResult` равен исходному результату, `improved: false`.
Участники №1/№2/№3 должны согласовать семантику и тесты до правки общих типов.
Это предложение в документации, **не реализованное поле HTTP-ответа**.

## Резервный режим: вопрос команде

Генератор готов и не импортирует SDK. Его результаты не подключены к HTTP/UI.
Согласованный контракт требует 503/502 при недоступности AI и не предусматривает
доставку структурированного резервного объяснения в ответе ошибки.

**Как передавать резервное объяснение пользователю: расширить ответ ошибки при
сохранении 502/503 либо согласовать успешный ответ с явным источником llm/fallback?**

До решения команды сервис не возвращает fallback вместо ошибки, не добавляет
полей в контракт и не помещает сериализованный анализ в `error.message`.
Нельзя импортировать серверный генератор в UI или считать резервный режим
доступным пользователю на основании одного теста функции.
Fallback объясняет только исходный расчёт, не подбирает новые решения и не является
успешным поиском AI-агента. Использование его шаблонов для фактов в завершённом
агентном отчёте не меняет это различие.

## Проверки без платных запросов

`npm test` выполняет Vitest: серверные тесты используют `node`, локальный mock
`server-only` и двойники. В `openai.test.ts` и `agent-sdk.test.ts` работает настоящий SDK,
но `fetch` полностью подменён. Используются только фиктивные тестовые ключ и модель.
Тесты проверяют успешное получение структуры объяснения, ошибки и HTTP-статусы.
Ни SDK, ни конфигурации тестирования ради этого не изменялись.

Команды: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, затем
`npm run test:smoke`. Для PowerShell при запрете скриптов — `npm.cmd`.

Проверено 23 сентября 2026 года после реализации агента: **86 тестов Vitest в 9 файлах**,
`lint`, `typecheck`, production `build` и **1 существующий Playwright smoke** — успешно.
Настоящий домен, живой OpenAI и получение объяснения в UI этими проверками не подтверждены.

Демонстрация последовательности из `agent.test.ts` (сценарная модель и искусственные
результаты двойника, **не живой запуск**, Score 60/61 не доменный эталон):

```text
1. get_city_context        → каталог организаторов
2. evaluate_scenario      → M7/M8/M10 Нура, M12 город, M5 Алматы → candidate-1, Score 60
3. evaluate_scenario      → M7/M8/M10 Нура, M12 город, M5 Есиль  → candidate-2, Score 61
4. compare_scenarios      → original / candidate-2 → разница +4.45693
5. финальный ответ модели → selectedScenarioId = candidate-2
   серверный отчёт        → исходные решения не изменены, альтернатива в рекомендациях
```

Отдельный тест начинает с невалидного набора, передаёт модели доменные причины
без Score, затем проверяет исправленный вариант. Также проверены кэш перестановок
и отказов, отсутствие улучшений, неверные инструменты/ID/аргументы, ложные числовые
поля модели, лимиты 6/12/45 секунд, отказ/неполный ответ/ошибка провайдера,
HTTP 429 без повторов SDK, токены, компромиссы и неизменность исходного результата API.

Единственный текущий Playwright smoke оставлен без изменения. Он проверяет
production-страницу и ответ 501. Это проверка каркаса, **не успешного AI-анализа**.
Платный запрос невозможен через текущую заглушку маршрута.

Когда участник №2 добавит настоящий AI-блок, способ проверки UI без оплаты:
перехватить браузерный `POST **/api/analyze` через `page.route`, вернуть согласованный
успешный `AnalyzeResponse` с фиксированными `result` и `analysis`, пройти реальный
путь пользователя и проверить отображение текста/чисел. Такой перехват действует
на браузерный fetch, а не автоматически на `request.post` или запросы Next.js к SDK.
Это успешный UI-тест с HTTP-двойником; он не подтверждает работу настоящего API.

Vitest-моки не действуют на production-сервер Playwright. Для полного сквозного
теста через настоящий Next.js с подменённым провайдером понадобится согласованный
способ серверного тестового подключения. Такого режима в каркас не добавлено.
Его нельзя заменять одной проверкой 503 и называть успехом. Изменение общего
smoke и согласование этого режима остаются задачей интеграции участников №2 и №3.
