## Инструментальный цикл

Модель получает достоверный исходный `SimulationResult` и цель улучшить Score.
Она выбирает следующий инструмент и аргументы, затем получает фактический ответ:

1. `get_city_context({})` — исходные районы, каталог, правила, эффекты, синергии и конфликты.
2. `evaluate_scenario({ scenario })` — вызов настоящего `engine.evaluate`.
   Невалидный кандидат получает `issues` без Score; модель может исправить предложение.
   Допустимый сохраняется под ID `candidate-N`; исходный — `original`.
3. `compare_scenarios({ leftId, rightId })` — сравнение только сохранённых допустимых
   результатов. Разницы стоимости и Score считает сервер.
4. Финал — строгий `{ selectedScenarioId }`, ссылающийся на лучший проверенный результат.
   При равенстве остаётся ранее сохранённый вариант. До финала необходима проверка
   хотя бы одного отличающегося кандидата.

Нет серверного списка заранее подготовленных альтернатив. Модель сама предлагает
меры и районы. Zod инструментов проверяет транспорт, а бизнес-правила и формулу —
только домен. В инструменте для городской меры `districtId: null` преобразуется в
отсутствие поля перед доменом; публичный HTTP-контракт по-прежнему требует отсутствие.

Неизвестные инструменты, некорректные аргументы и придуманные ID не исполняются.
Результаты сопоставляются по уникальному `call_id`. Перестановка мер не создаёт
нового кандидата; допустимые и невалидные повторные наборы берутся из кэша.
Исходные решения не изменяются. Требование «пять направлений» не превращается в
правило «по одной мере каждого»: организаторы требуют пять мер и максимум две
одного направления, то есть минимум три направления.

Произвольные числовые утверждения модели не отображаются. Она выбирает проверенный
ID, а сервер формирует текст из реестра: меры/районы, Score, изменение, бюджет,
слабейший район, критические значения и ухудшения отдельных показателей.
`strengths`, `risks`, `consequences` явно относятся к исходному сценарию;
альтернатива и её компромиссы находятся в `recommendations`. При отсутствии
улучшения вывод честно оставляет исходный вариант. Глобальный оптимум не обещается.

## Ограничения, токены и расходы

- Не больше 6 генераций модели и 12 вызовов инструментов за запуск.
- `max_output_tokens: 2000`, включая невидимые выходные токены модели.
- 45 секунд на весь цикл, включая предварительный подсчёт токенов. Каждый запрос
  ограничен остатком дедлайна и максимумом 20 секунд общей фабрики.
- `maxRetries: 0` отдельно на агентных запросах; скрытых повторов SDK нет.
- До отправки проверяется полный сериализованный запрос: максимум 128 000 UTF-8
  байт, включая историю, инструкции, схемы инструментов и финального ответа.
  Максимум 64 000 байт возвращённого `output`; превышение останавливает цикл.
- История не обрезается незаметно: `truncation: "disabled"`. Байтовый лимит —
  ограничение контекста/памяти, **не оценка токенов или денег**.

Ручная проверка требует `AgentBudgetPolicy`: `maxUsd <= 1`,
`maxInputTokens <= 16000`, точное имя модели, входной/выходной тариф за миллион
токенов, официальный источник и время проверки тарифа не старше 24 часов.
Тариф по умолчанию отсутствует. Источник в политике — запись проверки оператором,
а не доказательство того, что программа сама скачала и проверила прайс.

В бюджетном режиме перед **каждой** генерацией вызывается
`client.responses.inputTokens.count` с тем же контекстом, инструкциями, инструментами
и схемой ответа. После проверки входного лимита резервируется стоимость полного
входа и максимально возможных 2000 выходных токенов. Если остатка бюджета не хватает,
следующая генерация не отправляется. Резервы не возвращаются даже после более
короткого ответа или сетевой ошибки. Расчёт ведётся в целых нанодолларах с округлением вверх.

Запросы используют `service_tier: "default"`. Для реального прогона нужно проверить
именно соответствующий тариф выбранной модели, включая возможные условия длинного
контекста/дополнительных начислений. Неясный тариф или шлюз — повод запросить
согласование, а не придумать цену. В тестах используются **искусственные тарифы**.
Подсчёт токенов — отдельный endpoint, до 6 обращений, он не генерирует ответ модели;
его число отдельно видно в `tokenCountRequests`. Сетевых повторов у него тоже нет.

`runScenarioAgent` без опции `budget` сохраняет обычную совместимую работу сервиса
с ограничениями итераций/контекста/времени, но **не обещает долларовый предел**.
Production API использует этот режим. Для разрешённой проверки до $1 используется
только `runLiveAgentCheck`, где бюджет обязателен; не заменять его обычным POST.

`usage` хранит суммы `input_tokens`, `output_tokens`, `total_tokens`, cached/reasoning
и usage каждого полученного ответа, включая неполные. `complete: false` означает,
что хотя бы один отправленный запрос не имеет usage. Его нельзя выдавать за нулевой расход.
В бюджетном режиме отсутствие/несогласованность usage останавливает продолжение;
`budget.estimatedUsd` становится `null`, резерв сохраняется. Известная оценка
использует полный входной тариф без скидки кэша: это консервативная оценка, не квитанция.

При отказе, неполном ответе, лимите, неверном финальном ID или ошибке провайдера
незавершённый поиск не выдаётся как улучшение. Синхронный доменный расчёт нельзя
прервать таймером посреди исполнения; сразу после него дедлайн проверяется повторно.

Основания: [OpenAI Docs: Function calling](https://developers.openai.com/api/docs/guides/function-calling),
[Counting tokens](https://developers.openai.com/api/docs/guides/token-counting).

## Ключ, endpoint и отдельный ручной запуск

Локально добавьте в `.env.local` значения `OPENAI_API_KEY` и `OPENAI_MODEL` из
существующего `.env.example`. Не присылайте ключ в чат, не используйте `NEXT_PUBLIC_*`.
`.env*` уже исключены из Git, кроме пустого примера. Проверка наличия настроек
не печатает ключ. Авторизация самого Codex не используется.

SDK может учитывать `OPENAI_BASE_URL`; агент проверяет фактический `client.baseURL`.
Сейчас разрешён только `https://api.openai.com/v1` (с завершающим `/` или без него),
без credentials, query и fragment. Несогласованный шлюз блокируется до сети.
Шлюз хакатона требует отдельной проверки адреса, тарифа, модели и Responses API.

`runLiveAgentCheck` — серверная функция, не автоматический CLI/тест. Она не вызывается
при `npm test`, build, CI или через production-маршрут. Явный ручной вызов получает
сценарий и проверенную политику цен; модель берётся только из серверного окружения.
До него нужно проверить тариф выбранной модели по официальной странице и убедиться,
что весь разрешённый прогон укладывается в $1. Не подставлять тестовые тарифы.
Если лимит/тариф нельзя надёжно оценить — сначала согласовать с пользователем.

Функция заново рассчитывает исходный сценарий настоящим импортированным движком,
выполняет единственный агентный цикл и возвращает отчёт. После ошибки повторного
платного прогона нет. При успехе `source: "openai-agent"`; при ошибке
`status: "failed", source: "local-fallback"` и отдельное резервное объяснение.
Этот внутренний отчёт не является изменением `AnalyzeResponse`.

Отчёт включает время, модель, исходный/лучший результаты, selected ID, журнал,
usage и оценку бюджета. Журнал сохраняет проверенные сценарии, ошибки и конкретные
сравнения ID/Score/стоимости. `usage.responses[].toolResultCallIds` показывает,
результаты каких инструментов были включены в соответствующий запрос модели.
Это наблюдаемые действия/данные, не скрытые рассуждения. Ключи, сырой ответ провайдера
и encrypted reasoning в отчёт не попадают.

## HTTP и подключение интерфейса — участник №2

`POST /api/analyze`, JSON соответствует существующему `AnalyzeRequest`:

```json
{"scenario":{"decisions":[{"measureId":"M7","districtId":"nura"},{"measureId":"M8","districtId":"nura"},{"measureId":"M10","districtId":"nura"},{"measureId":"M12"},{"measureId":"M5","districtId":"saryarka"}]}}
```

Не отправлять ключ, Score, стоимость, эффекты или инструкции модели.
Лишние поля оболочки отклоняются; структуру сценария и правила проверяет домен.
Невалидный исходный сценарий не вызывает OpenAI и не получает Score.

| HTTP | Смысл |
| --- | --- |
| 200 | `{ ok: true, result, analysis }`: `result` всегда исходного сценария; альтернатива — в тексте `analysis.recommendations` |
| 400 | `INVALID_REQUEST`: некорректный JSON, оболочка либо доменный `INVALID_SHAPE` |
| 422 | `INVALID_SCENARIO`: доменные `error.issues`, индексы решений с нуля |
| 503 | `AI_NOT_CONFIGURED`: отсутствует ключ или модель |
| 502 | `AI_UNAVAILABLE`: недоступность AI, отказ, лимиты, неверный ответ |
| 500 | `INTERNAL_ERROR`: безопасное сообщение при внутренней ошибке, включая исключение движка |

Ошибки: `{ ok: false, error: { code, message, issues? } }`, без `result`/`analysis`.
Сервер заново считает по исходному датасету и передаёт сервису копию результата.
`contributions` — эффекты до clip, не аддитивные вклады в Score.

В UI отправить сценарий через `fetch` с `AbortSignal`, сначала проверить `payload.ok`.
При успехе отобразить `summary` и массивы `strengths`, `risks`, `consequences`,
`recommendations` обычным React-текстом, без `dangerouslySetInnerHTML`.
При ошибке показать безопасное сообщение/доменные issues и сохранить локальный расчёт.
Во время запроса — skeleton и защита от повторной отправки. При изменении решений
увеличить версию сценария, отменить старый запрос и убрать старое объяснение.
Ответ/ошибку/loading применять только для всё ещё актуальной версии.
Отмена браузерного fetch сама по себе не гарантирует отмену обращения к провайдеру.

Карточки и графики берут числа из `result.baseline/after/budget/scoreDelta`, а не из
строк AI. Заголовок рекомендаций — «AI-агент: поиск альтернативы». Исходный набор
не заменяется автоматически. По текущему контракту альтернативу можно перенести
в форму вручную и пересчитать. Не парсить строки для кнопки «Применить».
Сейчас `ProjectShell` не реализует этот пользовательский путь.

## Оставшиеся вопросы контракта

1. **Fallback в интерфейсе.** Генератор сохранён, но 502/503 не содержат анализа.
   Команде нужно выбрать расширение ответа ошибки либо успешный ответ с явным
   источником `llm/fallback`. До согласования API не подменяет ошибку успехом,
   не добавляет скрытый JSON в строки и не импортирует серверный генератор в UI.
   Резервное объяснение не является поиском агента.
2. **Структурированная альтернатива.** Для применения/сравнения рекомендуется
   согласовать необязательное поле успешного ответа:
   `agent?: { bestScenarioId: string; bestResult: SimulationResult; improved: boolean }`.
   `result` остаётся исходным, решения берутся из `bestResult.scenario`. Сейчас
   это только предложение, не реализованное расширение HTTP-контракта.

## Бесплатные проверки

Автоматические серверные тесты используют `node`, mock `server-only`, фиктивные
ключ/модель и подменённый `fetch`/SDK. Сценарии для протокольных тестов могут иметь
искусственные Score 60/61 и искусственные цены; они не являются эталонами домена.
Базовая фикстура теперь получается из настоящего `evaluateScenario`.
`route.test.ts` и `live-agent-check.test.ts` проверяют настоящий движок + агент +
официальный SDK, но не живые ответы OpenAI.

Проверяются реальные невалидные/дорогие сценарии, коррекция кандидата после отказа,
неизвестные инструменты, кэш, лучший проверенный ID, отсутствие улучшений/мутаций,
компромиссы, лимиты 6/12/45 секунд, размер контекста/ответа, входные токены, денежный
бюджет, неподтверждённый тариф/endpoint, usage, сбой/отказ/неполный ответ и отсутствие
скрытых повторов SDK.

Команды: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, затем
`npm run test:smoke`; при ограничениях PowerShell использовать `npm.cmd`.
Итоговый прогон 23 сентября 2026: **198 тестов Vitest в 13 файлах**, lint,
typecheck и production build — успешно. **1 Playwright smoke** — успешно.
После зависания завершения процесса в Windows-песочнице smoke повторён вне неё
и завершился с кодом 0. В этих проверках нет платных обращений к OpenAI.

Единственный Playwright smoke проверяет production-страницу и настоящий HTTP 422
для невалидного сценария. Он гарантированно не обращается к OpenAI и **не подтверждает
успешное получение объяснения пользователем**. После UI-интеграции для бесплатного
успешного UI-теста перехватить браузерный `POST **/api/analyze` через `page.route`,
вернуть валидный `AnalyzeResponse` и проверить отображение. Это тест UI с HTTP-двойником.
Vitest-моки не действуют на сервер Playwright; для полного server-to-provider e2e
нужно отдельное согласованное серверное тестовое подключение. 503 не заменяет успех.
