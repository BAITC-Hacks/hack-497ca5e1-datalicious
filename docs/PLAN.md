# План командной работы

## Этап 0 — общий каркас

Есть документация, данные, типы, серверная граница SDK, стартовая страница,
заглушка API и инструменты проверки. Формула, валидатор, форма выбора
и AI-анализ — следующие задачи.

После публикации каркаса в main каждый участник выполняет:

```sh
git fetch origin
git switch main
git pull --ff-only origin main
npm ci
```

Затем создаёт свою ветку:

| Участник | Команда | Зона изменений |
| --- | --- | --- |
| 1 — данные и модель | `git switch -c feat/domain-score` | `src/data`, `src/domain`, тесты |
| 2 — интерфейс | `git switch -c feat/simulator-ui` | `src/components`, page/layout/CSS, UI-тесты |
| 3 — AI и API | `git switch -c feat/ai-analysis` | `src/server`, `src/app/api/analyze`, тесты |

## Этап 1 — параллельная реализация

Участник 1: Zod-валидатор структуры и бизнес-правил, `SimulationEngine`, чистый
Score, baseline и дельты. Проверить бюджет 100/101, 4/5/6 решений, повторы,
неизвестные ID, район обязателен/запрещён, лимит направления, три конфликта,
городские эффекты, лаги, синергии без лагов, отрицательный T1 у M11, clip,
строгое `<40`, отсутствие мутаций, инвариантность к перестановке решений.
Контроль: база 52.55768, пример 56.54307 при стоимости 95; сравнивать с допуском.

Участник 2: пять решений, каталог всех направлений, выбор района, остаток бюджета,
ошибки, baseline/after, Recharts и AI-объяснение. Черновик редактируется, отправка
невалидного набора запрещена. Проверить клавиатурную доступность, пустой/частичный
сценарий, загрузку и ошибку AI. До готовности домена использовать явно обозначенные
фикстуры по общим типам; после интеграции подключить движок без дублирования формулы.

Участник 3: `AnalysisService`, промпт по готовым фактам, Zod-проверка ответа,
тайм-ауты, API по ARCHITECTURE. Проверить malformed JSON, невалидный сценарий,
отсутствие конфигурации, mock success, ошибку провайдера, невалидную структуру
ответа и отсутствие утечек. До готовности домена использовать mock `SimulationEngine`
в тестах. Итоговый API считает по серверным данным и не доверяет клиентским числам.

## Этап 2 — интеграция

1. Согласовать изменения `types.ts` небольшим PR до зависимых изменений.
2. Влить домен; обновить ветки UI и AI из main.
3. Подключить UI и сервер к одному движку и общим контрактам.
4. Заменить smoke итоговым потоком с примером организаторов и mock AI.
5. Проверить изменение Score при изменении решений, отказ невалидным наборам
   и доступность детерминированного расчёта при недоступном AI.
6. Обновить README: запуск, демо, ограничения и архитектура.

## Готовность PR и демо

Перед PR: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`.
Перед итоговым объединением: `npx playwright install chromium`, `npm run test:smoke`.
Тесты без платных запросов; реальную проверку AI выполнять отдельно с серверными
переменными. Ключи не коммитить.

Общие конфиги, зависимости, lock-файл и контракты менять согласованно.
Участники отправляют свои ветки и открывают PR в main. Без force-push общей истории.
